| D1 — Does tenant_id go, denormalised, on the six tables that have no tenant column? | Verified by reading the DDL: `listings` has only product_id, `listing_versions` only listing_id, `validation_runs` only listing_id, `agent_runs` only a NULLABLE product_id, `performance` only listing_id, `audit_log` only `actor UUID REFERENCES users(id)`. None can be filtered by tenant without a 1–3 table join. Meanwhile invariant #6 says every query filters by tenant and the spec's own repository base class does `query.filter(model.tenant_id == self.tenant_id)` — on these six models that attribute does not exist, so either the query crashes or someone writes a join-based override, forgets the join once, and tenant A's approved listing is published to tenant B's seller account. That is an unrecoverable, customer-visible breach and the risk register's only Critical entry. After migration 0001 ships, backfilling tenant_id onto a populated listings/audit_log table plus rewriting every FE and AI query is a multi-day rework. | YES. Add `tenant_id UUID NOT NULL REFERENCES tenants(id) ON DELETE CASCADE`, indexed, to all six in migrations 0001/0002, and kill denormalisation drift at the DB level with composite foreign keys — `FOREIGN KEY (tenant_id, listing_id) REFERENCES listings (tenant_id, id)` — which costs one extra `UNIQUE (tenant_id, id)` index per parent table and is free at MVP scale. `rules` stays global by design (Amazon/Flipkart rules are platform-wide) with a NULLABLE tenant_id reserved for Phase-2 overrides, despite the ER diagram saying `Tenant \|\|--o{ Rules : configures`. Add Postgres RLS in week 2 (migration 0006) as a second layer, NOT as a substitute — RLS still needs the column, only works when the app connects as a non-owner role, and requires `SET LOCAL` inside a transaction or a pooled connection carries one tenant's GUC into the next tenant's request. | TODAY, Tue 22 Sep (Day 2) — before a single line of migration 0001 is written on Day 4. |

| D3 — CanonicalListing is defined twice, incompatibly. Nested or flat? | Spec [35] (05-listing-generation.md) is NESTED: `{listing_id, product_id, marketplace, category, status, content:{title,bullets,description}, keywords:{...}, attributes, image_reports:[], confidence_score, version:1, created_at}`. Spec [06] (the build plan) is FLAT: top-level title/bullets/description, `images:[{image_id,slot}]`, `generated_by`, `schema_version:'1.0'`, and no listing_id, category, status or created_at. A third partial shape exists in AgentState as generated_content/generated_keywords/generated_attributes. This is the object the AI team's merge node writes, the Rules Engine reads, the FE renders and the adapters map — three teams cannot start until it is one shape. | NESTED, for a mechanical reason: each nested block is exactly one parallel agent's output object (the Content Agent returns `{title, bullets, description}`, the Keyword Agent returns `{search_terms, ...}`), so merge_outputs becomes one assignment per agent instead of a spread that can silently clobber sibling keys — and it gives the correction loop an addressable path (`content.title`) that the flat shape cannot express once `attributes` contains a key named 'title'. Borrow three fields from the flat version: `images:[{image_id, slot, position}]` (pointers only), `generated_by_agent_run_id`, and `schema_version`. Keep `version` (int, listing_versions.version) and `schema_version` (semver string) as DISTINCT fields — the specs put two concepts in one slot. ImageReports are a SIBLING payload, not a field of the listing: the DB already settles it with two separate JSONB columns, content_json and image_reports_json, and nesting reports would mean rewriting the whole content_json every time a user re-uploads one image. Also rename `keywords.backend_keywords` → `keywords.hidden_terms` today: it is Amazon seller-central jargon and spec [42] itself marks it 'Not applicable' for Flipkart, making it the one genuine violation of invariant 5 in the canonical model. Free today; expensive on Day 20 when it lives in prompts, FE labels, JSONB and adapter mapping tables. | EOD Wed 23 Sep (Day 3). The AI team cannot write the merge node until it lands. |

| D5 — How does the backend invoke the AI pipeline: in-process, or a separate service? | This is the seam where a three-team split most easily turns into two incompatible systems. If the AI team stands up their own Cloud Run service, we get a second deploy unit, duplicated state, ~150ms per node, a second auth path to secure, and — worst — a team that can open its own DB session, which puts tenant scoping one forgotten `.filter()` away from a cross-tenant leak and leaves the Day-41 audit nothing to audit. | IN-PROCESS inside the ARQ worker, which is the spec's own answer stated twice (build-plan §5: "AI Orchestration: LangGraph — In-process / ARQ Worker"; §7: "The LangGraph graph executes in-process on the background worker"; Day 26: "/listings/generate invokes graph asynchronously via ARQ worker"). The AI team ships `packages/pipeline` exposing exactly one entry point, `async def run_listing_pipeline(state: AgentState, deps: PipelineDeps) -> GenerationResult`. `deps` is a Protocol WE implement (retrieve_brand_chunks, load_rules, load_category_template, validate_rules, validate_images, record_agent_run, emit_node_event, get_model_credentials); the AI package imports no SQLAlchemy, no FastAPI, opens no session, reads no os.environ and never sees marketplace_accounts — enforced by an import-linter contract forbidding `packages.pipeline -> apps.api`. Their LangGraph checkpointer gets its own isolated store (Redis, or a `langgraph_checkpoints` table never joined to business tables). Our worker persists listing_versions, validation_runs and agent_runs from the returned GenerationResult in ONE transaction, so tenant filtering happens in exactly one place. Escape hatch if they insist on a service: Cloud Run with service-to-service OIDC, POST /pipeline/v1/run plus a callback — the port interface makes it a one-adapter swap later, so we lose nothing by starting in-process. Tell them explicitly and in writing that the graph has NO publish node and NO approval node (it ends at quality_check returning NEEDS_APPROVAL or BLOCKED), because spec [16]'s node table lists `await_approval` and `publish` as graph nodes and directly contradicts invariant 1 — and [16] is the document they will build from. | Wed 23 Sep (Day 3); AgentState field list, PipelineDeps signatures, ErrorReport ownership per source and the exact node-event name strings all FROZEN with the AI team by Fri 25 Sep (Day 5). |
| D6 — Who signs the JWT: FastAPI or NextAuth? | Specs [116]/[154]/[157] say only "JWT via NextAuth (self-hosted)" and build-plan Day 6 says "JWT authentication with NextAuth bridge" — neither says who signs. If NextAuth mints it, the FE team owns our security boundary and FastAPI must verify NextAuth's encrypted JWE (A256GCM with a key HKDF-derived from NEXTAUTH_SECRET), which PyJWT cannot do without reimplementing their derivation. With separate FE and BE teams this ambiguity will produce two incompatible implementations built against opposite assumptions, discovered in week 4. | FastAPI is the SOLE issuer. `POST /api/v1/auth/login` validates email+password and returns `{access_token, refresh_token, expires_in, user}`; NextAuth runs a CredentialsProvider whose authorize() calls that endpoint and holds our tokens as an opaque session credential, forwarding `Authorization: Bearer <our access_token>`. HS256 with JWT_SECRET from Secret Manager (the Day-3 Secret Manager seed list contains a singular JWT_SECRET, which implies symmetric); access 30 min, refresh 14 days, rotating with reuse detection. Claims frozen as `{sub, tid, roles[], email, typ, jti, iss, aud, iat, exp}` — always a roles ARRAY of length one even though users.role is a single column, so multi-role later needs no FE change. `tid` is the only source of tenant identity; no endpoint ever reads tenant_id from a body, query string or header. Move to RS256 + /.well-known/jwks.json in Phase 2 when a second consumer exists. FE consequence they must plan for: a silent-refresh branch in the NextAuth jwt() callback, not just a session read. Also settle NextAuth v4 vs v5/Auth.js on Day 3 — the APIs are incompatible and the specs name no version. | Wed 23 Sep (Day 3), as ADR-0003 — before the FE builds /login on Day 7, not on Day 6 when both teams have already built. |
| D7 — Listing status: 9 lowercase values or 14 uppercase pipeline states? | Three incompatible state machines exist. The DDL comment on listings.status: created\|generating\|validated\|needs_review\|approved\|publishing\|published\|blocked\|failed (9, lowercase). The build-plan §07 state diagram: QUEUED, LOADING_CONTEXT, GENERATING, SCHEMA_VALIDATING, RULE_VALIDATING, VISION_VALIDATING, CORRECTING, QUALITY_CHECK, NEEDS_APPROVAL, APPROVED, PUBLISHING, PUBLISHED, BLOCKED, FAILED (14, uppercase). Spec [17] has a third set. Three teams render or write this field. | Split them. The 9 coarse lowercase values are the PERSISTED `listings.status` — that is the set with a database constraint behind it, it is what the FE filters on and what we index. The 14 fine-grained states become LangGraph node names surfaced as a separate, non-persisted `stage` on the JobEnvelope, which is what a progress spinner renders. Enforce the coarse set with a CHECK constraint, not a Postgres ENUM type (adding a value to an ENUM inside a transaction is painful; a CHECK is a one-line ALTER). Both sets ship as shared Pydantic StrEnums in packages/schemas generating the TypeScript union — the FE must never hand-maintain a parallel list. | TODAY, Day 2 — it is in packages/schemas v1.0.0. |
| D8 — One job-state vocabulary, and where job state actually lives | Spec [131] says QUEUED → RUNNING → COMPLETED \| FAILED \| TIMEOUT; build-plan §10 says QUEUED → RUNNING → SUCCEEDED / FAILED / PARTIAL. COMPLETED vs SUCCEEDED is a naming coin-flip, but PARTIAL is load-bearing for invariant 12 (per-field publish retry). Worse: there is no jobs table anywhere in the 13-table schema, so job state would live only in Redis — and ARQ keeps results at `arq:result:<id>` under a keep_result TTL while Memorystore Basic has no persistence and no failover, meaning one restart orphans every in-flight job and the FE polls a 404 forever. | Vocabulary: `QUEUED → RUNNING → SUCCEEDED \| PARTIAL \| FAILED \| CANCELLED \| DEAD_LETTER`, with timeout as a failure REASON (`error_code: JOB_TIMEOUT`), not a state. PARTIAL applies only to publish and import jobs. Ship it as one StrEnum in packages/schemas so the FE's badge component and the AI team's status writes use identical strings. Storage: a durable `job_runs` table (migration 0003) written inside the same transaction as the domain change, and `GET /api/v1/jobs/{job_id}` reads THAT, never ARQ's Redis result. Canonical polling endpoint is `/api/v1/jobs/{job_id}`; keep the spec's `GET /listings/{id}/status` as an alias returning the identical JobEnvelope for that listing's newest job — the spec's only status endpoint is keyed by listing id, which cannot poll a bulk import (no listing exists yet) or a publish job. One JobEnvelope, one FE polling hook, four job kinds. No webhooks in MVP: [106] says the client "polls for status or receives a webhook callback" while [115] scopes the whole webhook system to Phase 2 — [115] wins; tell the FE so they do not build a receiver. Return `Retry-After` as a hint (2s RUNNING, 5s QUEUED, absent on terminal). | Wed 23 Sep (Day 3) — before migration 0003 and before the FE writes their polling hook. |
