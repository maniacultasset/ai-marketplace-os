## Why the queue switch (key facts)

- **ARQ is maintenance-only (#510, 2025-10-18).** Its 2026 releases only add Python versions, it pins
  `redis<6` (so redis-py 5.3.1 from 2025-07), and several bug fixes are unmerged (#508, #531, #498).
- **The Canon already rebuilds half a queue in Postgres around ARQ:**
  - `job_runs` as the source of truth;
  - commit-then-enqueue;
  - a 60 s sweeper for the dual-write gap;
  - a self-built dead-letter queue;
  - a log-line metric.

  All of that exists because Memorystore Basic is an ephemeral cache with no failover.
- **procrastinate ≥3.8 enqueues inside the same transaction as the domain rows.** The skeptic
  verified this locally on SQLAlchemy 2.0.54 async + psycopg 3.3.6 + procrastinate 3.10.0 + PG16:
  rollback leaves 0 rows in both tables, commit leaves 1 in each, and a worker drains the job. That
  removes the sweeper and the dual-write bug class.
- **One managed service fewer per environment:** about $36/mo per Memorystore 1 GiB instance at list
  price, plus Direct VPC egress setup for Redis. That matters for a bootstrapped client and a team
  with no SRE.
- **Costs of switching:**
  - The async driver changes to psycopg 3, which overturns the Addendum's "asyncpg only" freeze.
  - procrastinate has no per-task timeout (#1281), so every task needs an `asyncio.timeout` wrapper
    that maps to `JOB_TIMEOUT`.
  - Future IAM DB auth via the Cloud SQL connector supports async only with asyncpg (deferred
    anyway, Canon row 53).
