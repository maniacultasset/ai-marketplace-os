## AUTONOMOUS LISTING AGENT

V1 Business Requirements & End-to-End Listing Process (Apparel / Fashion Marketplace Sellers)

Important Notice on Living Marketplace Rules

Marketplace schemas, required fields, allowed values and validation rules change. The product must therefore treat marketplace requirements as living rules rather than a one-time hard-coded field list. Amazon explicitly provides marketplace/ product-type schemas and notes that requirements can change; Flipkart likewise states that listing rules are subject to change.

### Purpose of this Document

Define, in non-technical business language, exactly what the product must collect, understand, create, validate, submit, monitor, repair and report when a seller wants to publish an apparel SKU across marketplaces from one dashboard.

Item

Definition

**V1 product promise**

Seller gives basic brand + product information once. The agent turns it into marketplace-ready listings and manages the listing lifecycle until the listing is live or a human decision is genuinely required.

**Primary niche**

Apparel / fashion products.

**Primary user**

D2C brands, manufacturers, traders, small sellers and marketplace agencies managing apparel catalogs.

**Core outcome**

One product source of truth → marketplace-specific listing → validation → submission → error resolution → live confirmation.

**Operating principle**

Do not ask the seller for information the system can reliably derive, reuse or validate. Ask only when missing information materially blocks a correct listing.

## 1\. Product in One Sentence

"The Autonomous Listing Agent is a listing operations agent, not merely a content generator. It takes a seller's product information and assets, builds a canonical product record, maps that product to each marketplace's category and field structure, generates or transforms listing content, validates completeness and compliance, submits the listing, reads marketplace responses, fixes resolvable errors, asks the seller only for unresolved information, resubmits, and confirms the final live status."

## 4\. Marketplace Strategy

V1 should be designed around a common apparel product model plus marketplace-specific adapters. The common model is the source of truth. Each marketplace adapter decides which fields are required, optional, conditionally required, allowed values, formatting rules, variation rules and submission/status behavior.

*   **Target marketplace set:** Can include **Amazon, Flipkart, Myntra, AJIO, Meesho and Nykaa Fashion**, subject to the commercial/API access available to the business.
*   **Category Semantic Variance:** Do not assume that the same apparel category means the same thing on every marketplace.
*   **No Hard-Coded Lists:** Do not hard-code a single universal 'required fields' list.
*   **Dynamic Schemas:** For each connected marketplace, the product should maintain a current marketplace/category schema and map the canonical product into it.
*   **Amazon Documentation:** Amazon's current developer documentation describes Product Type Definitions as the source for product-type and marketplace requirements, including required/conditional attributes.
*   **Flipkart Documentation:** Flipkart's official Listing Management documentation similarly separates product information from the seller listing and states that listing rules can change, so errors should be handled explicitly.

## 7\. Variants: The Product Family Model

The system must distinguish the product style from the sellable variant. A common apparel family is one style with multiple colors and sizes.

Level

Example

Rule

**Parent / style**

`TSHIRT-001`

Represents the underlying product/style.

**Color child**

`TSHIRT-001-BLK`

One color variation.

**Size child**

`TSHIRT-001-BLK-M`

One sellable size/color combination.

**Marketplace listing**

Marketplace-specific SKU/listing ID

External representation of the sellable item.

### Core Variation Invariants

*   Store a complete **size × color matrix**, including unavailable combinations.
*   **Never silently create a variant** that the seller did not provide.
*   **Keep seller SKU stable** even if marketplace identifiers differ.
*   **Record parent-child relationships separately** from marketplace-specific variation rules.
*   Amazon's listing schema explicitly distinguishes parent and child listing levels, with different attributes applicable to each.

## 12\. Step-by-Step Autonomous Listing Workflow

STEP 1

### UNDERSTAND PRODUCT

**Goal:** Build a complete understanding of the product before generating a marketplace listing.

**Inputs:** Seller form, spreadsheet, images, website/catalog data, size chart, product documents and connected systems.

**Actions:** Identify product and variants; separate facts from marketing language; detect missing/conflicting/duplicate data; determine reliable vs confirmation-needed facts.

**Output:** Structured product facts with source and confidence.

STEP 2

### CLASSIFY

**Goal:** Decide the correct product category and sub-category for each marketplace.

**Actions:** Identify product type (T-shirt, shirt, dress, jeans, etc.); identify audience/gender; map canonical product to marketplace taxonomy; verify seller category eligibility; use evidence & rules (no random guesses).

**Output:** Canonical category + marketplace-specific category/product type + confidence.

STEP 3

### EXTRACT ATTRIBUTES

**Goal:** Populate all product attributes from the available evidence.

**Actions:** Extract color, size, fabric, fit, pattern, neckline, sleeve, length, closure, occasion; normalize synonyms into controlled values; preserve original seller value + normalized value; track source; detect contradictions (e.g., '100% cotton' vs 'cotton-poly blend').

**Output:** Complete canonical attribute set with missing/conflicting fields identified.

STEP 4

### FILL MARKETPLACE SCHEMA

**Goal:** Transform the canonical product into the exact field structure expected by each selected marketplace.

**Actions:** Load current marketplace/category schema; map canonical fields to portal fields; apply allowed-value enums; mark required, conditional, optional and unsupported fields; build parent/child variation structure; map media roles and content fields.

**Output:** Marketplace-ready draft for each marketplace.

STEP 5

### GENERATE CONTENT

**Goal:** Create customer-facing listing content from verified product facts.

**Create:** Title, bullets/key features, description, search keywords, size/fit copy, portal-specific content fields.

**Rules:** No unsupported claims; no invented specs; do not copy prohibited content; keep consistent factual identity while adapting tone/format to marketplace rules.

**Output:** Content package with source traceability.

STEP 6

### VALIDATE

**Goal:** Catch problems before marketplace submission.

**Validate Checklist:** Required fields present; allowed values; parent/child relationship valid; color & size consistency; image presence & association; price/MRP consistency; product identifier rules; HSN/tax fields; country of origin & manufacturer details; content policy checks; no conflicting facts.

**Output:** `PASS`, `BLOCKED`, or `NEEDS HUMAN INPUT` with field-level reasons.

STEP 7

### FIND MISSING DATA

**Goal:** Determine whether missing information can be recovered automatically.

**Try in this strict hierarchy:**

1.  Existing canonical product record.
2.  Same brand's trusted catalog conventions.
3.  Connected PIM/ERP/catalog.
4.  Existing marketplace listing owned by the seller.
5.  Seller-provided files/assets.
6.  Deterministic category mapping.
7.  Ask seller.

**Output:** Missing fields reduced to the smallest set genuinely required.

STEP 8

### ASK HUMAN ONLY WHEN NECESSARY

**Goal:** Ask the seller one clear question instead of sending them back to a large form.

**Examples:** _'What is the fabric composition: 100% cotton or 95% cotton / 5% elastane?'_, _'Please provide the size chart for this product.'_, _'Which MRP should be used for the black variant?'_, _'Please confirm whether this is a women\\'s or unisex product.'_

**Question Must Include:** Why information is required; which products/variants it affects; exact expected answer; optional safe suggestions.

**Post-Response:** Update canonical record and resume automatically from blocked step.

STEP 9

### SUBMIT

**Goal:** Send the validated listing to the selected marketplace(s).

**Actions:** Submit only required and permitted fields; record submission time and job ID/reference; store exact version submitted; update status from Draft/Ready to Submitted/Pending.

**Output:** Marketplace submission record.

STEP 10

### CHECK STATUS

**Goal:** Determine what happened after submission.

**Possible Outcomes:** Accepted/processing · Active/live · Rejected · Partially accepted · Missing information · Validation failure · Pending marketplace review · Account/category permission issue.

**Rule:** Keep checking until a terminal state is reached or a human action is required.

STEP 11

### FIX ERRORS

**Goal:** Diagnose and resolve errors without making the seller repeat the process.

**For every error:** Capture error code/message; identify affected SKU/field; translate to plain language; determine if auto-fixable; apply deterministic fix; revalidate.

**Auto-Fixable Classes:** Wrong portal enum mapped from known canonical value; formatting issue; safely calculable derived field; incorrect parent/child mapping.

**Human-Required Classes:** Missing factual product info; conflicting seller data; brand authorization/approval; account issue; compliance evidence request.

STEP 12

### RESUBMIT

**Goal:** Send the corrected listing back to the marketplace.

**Actions:** Keep same seller SKU/identity; record correction made; increment submission attempt count; submit only after validation passes; preserve failed versions for audit.

STEP 13

### CONFIRM LIVE

**Goal:** Confirm the product is genuinely sellable/live.

**Minimum Confirmation:** Status = live/active; marketplace ID captured; seller SKU mapped; variant status captured; live URL captured where available; latest successful sync timestamp recorded.

**Output:** `LIVE` status.

STEP 14

### SHOW DASHBOARD STATUS

**Goal:** Give the seller a simple operational view.

**Show:** Overall status; per-marketplace status; current step; issue count; human actions required; last sync; marketplace listing ID/SKU; live URL; attempt history.

Core Dashboard Mandate

The dashboard should answer: _"What is live, what is not live, why, and what do I need to do?"_

### 15.1 Error Resolution Loop

27.  Capture error exactly as returned.
28.  Normalize it into an internal error category.
29.  Identify affected field/variant/listing.
30.  Determine whether the error is deterministic and safely fixable.
31.  Apply fix if safe.
32.  Re-run validation.
33.  Resubmit.
34.  If still failing, stop repeated retries and escalate.
35.  Show the seller the exact remaining action.

Important Anti-Loop Rule

The agent must never repeatedly submit the same failed listing indefinitely. Every retry needs a changed input, a known retryable condition, or a marketplace status transition that justifies another attempt.

## 16\. Human-in-the-Loop Rules

The product should be autonomous by default, but not reckless. Human involvement is a controlled exception.

Ask the Seller When

Do NOT Ask When

A critical factual field is genuinely missing.

The answer already exists in the canonical record.

Two authoritative sources conflict.

The value can be deterministically normalized.

Marketplace requires seller-specific approval/evidence.

The agent can safely transform an existing value.

A compliance declaration cannot be verified.

The missing value is merely a formatting variation.

A category/brand permission decision is required.

The marketplace has a known mapping for the category.

Stage

What Happens

## 22\. V1 Acceptance Criteria

*   A seller can create a brand profile once and reuse it across products.
*   A seller can provide apparel product information through a structured form or bulk input.
*   The system can represent one style with multiple color/size variants.
*   Every important canonical attribute can retain its source and confidence.
*   The system can map one canonical product into marketplace-specific category/field structures.
*   The system can distinguish required, conditional, optional and unsupported fields.
*   The system can generate title, bullets, description and keywords from verified product facts.
*   The system can validate the product before submission and show blocking reasons.
*   The system can identify missing data and ask targeted human questions.
*   The system can submit a listing and record the submission attempt.
*   The system can read the resulting marketplace status/error.
*   The system can automatically fix defined deterministic error classes.
*   The system can retry safely without creating uncontrolled duplicate submissions.
*   The system can escalate unresolved issues to a human.
*   The system can confirm a listing as LIVE only after marketplace success confirmation.
*   The dashboard can show per-marketplace status, listing identifiers, issues and latest activity.
*   The system preserves history so the team can understand what changed and why.

## 24\. Handoff to Lead Engineer: What Must Be Clear Before Build

*   **Canonical product is the source of truth;** marketplace listings are derived representations.
*   **Marketplace schemas are versioned and can change.**
*   **Every field should have a source**, and critical facts should have confidence/evidence.
*   **Required fields are marketplace + category + context dependent.**
*   **Variant relationships are first-class product data**, not just a UI feature.
*   **Listing status is per marketplace** and per variant where necessary.
*   **Errors are first-class records** with classification, severity and resolution state.
*   **Human questions are first-class workflow tasks**, not generic support tickets.
*   **Every submission and correction should be auditable.**
*   **The workflow must be resumable.** If a seller answers one question, the agent continues from the blocked step rather than restarting the entire job.
*   **The agent must be idempotent at the business level:** repeated status checks or safe retries should not create duplicate product identities.
*   **Preserve separation:** The system should preserve marketplace-specific data without polluting the canonical product with marketplace-only fields.

## 4\. Marketplace Strategy

*   **Category Semantic Variance:** Do not assume that the same apparel category means the same thing on every marketplace.
*   **No Hard-Coded Lists:** Do not hard-code a single universal 'required fields' list.
*   **Dynamic Schemas:** For each connected marketplace, the product should maintain a current marketplace/category schema and map the canonical product into it.
*   **Amazon Documentation:** Amazon's current developer documentation describes Product Type Definitions as the source for product-type and marketplace requirements, including required/conditional attributes.

## 12\. Step-by-Step Autonomous Listing Workflow

STEP 1

### UNDERSTAND PRODUCT

**Goal:** Build a complete understanding of the product before generating a marketplace listing.

**Inputs:** Seller form, spreadsheet, images, website/catalog data, size chart, product documents and connected systems.

**Actions:** Identify product and variants; separate facts from marketing language; detect missing/conflicting/duplicate data; determine reliable vs confirmation-needed facts.

**Output:** Structured product facts with source and confidence.

STEP 2

### CLASSIFY

**Goal:** Decide the correct product category and sub-category for each marketplace.

**Actions:** Identify product type (T-shirt, shirt, dress, jeans, etc.); identify audience/gender; map canonical product to marketplace taxonomy; verify seller category eligibility; use evidence & rules (no random guesses).

**Output:** Canonical category + marketplace-specific category/product type + confidence.

STEP 3

### EXTRACT ATTRIBUTES

**Goal:** Populate all product attributes from the available evidence.

**Actions:** Extract color, size, fabric, fit, pattern, neckline, sleeve, length, closure, occasion; normalize synonyms into controlled values; preserve original seller value + normalized value; track source; detect contradictions (e.g., '100% cotton' vs 'cotton-poly blend').

**Output:** Complete canonical attribute set with missing/conflicting fields identified.

STEP 4

### FILL MARKETPLACE SCHEMA

**Goal:** Transform the canonical product into the exact field structure expected by each selected marketplace.

**Actions:** Load current marketplace/category schema; map canonical fields to portal fields; apply allowed-value enums; mark required, conditional, optional and unsupported fields; build parent/child variation structure; map media roles and content fields.

**Output:** Marketplace-ready draft for each marketplace.

STEP 5

### GENERATE CONTENT

**Goal:** Create customer-facing listing content from verified product facts.

**Create:** Title, bullets/key features, description, search keywords, size/fit copy, portal-specific content fields.

**Rules:** No unsupported claims; no invented specs; do not copy prohibited content; keep consistent factual identity while adapting tone/format to marketplace rules.

**Output:** Content package with source traceability.

STEP 6

### VALIDATE

**Goal:** Catch problems before marketplace submission.

**Validate Checklist:** Required fields present; allowed values; parent/child relationship valid; color & size consistency; image presence & association; price/MRP consistency; product identifier rules; HSN/tax fields; country of origin & manufacturer details; content policy checks; no conflicting facts.

**Output:** `PASS`, `BLOCKED`, or `NEEDS HUMAN INPUT` with field-level reasons.

STEP 7

### FIND MISSING DATA

**Goal:** Determine whether missing information can be recovered automatically.

**Try in this strict hierarchy:**

1.  Existing canonical product record.
2.  Same brand's trusted catalog conventions.
3.  Connected PIM/ERP/catalog.
4.  Existing marketplace listing owned by the seller.
5.  Seller-provided files/assets.
6.  Deterministic category mapping.
7.  Ask seller.

**Output:** Missing fields reduced to the smallest set genuinely required.

STEP 8

### ASK HUMAN ONLY WHEN NECESSARY

**Goal:** Ask the seller one clear question instead of sending them back to a large form.

**Examples:** _'What is the fabric composition: 100% cotton or 95% cotton / 5% elastane?'_, _'Please provide the size chart for this product.'_, _'Which MRP should be used for the black variant?'_, _'Please confirm whether this is a women\\'s or unisex product.'_

**Question Must Include:** Why information is required; which products/variants it affects; exact expected answer; optional safe suggestions.

**Post-Response:** Update canonical record and resume automatically from blocked step.

STEP 9

### SUBMIT

**Goal:** Send the validated listing to the selected marketplace(s).

**Actions:** Submit only required and permitted fields; record submission time and job ID/reference; store exact version submitted; update status from Draft/Ready to Submitted/Pending.

**Output:** Marketplace submission record.

STEP 10

### CHECK STATUS

**Goal:** Determine what happened after submission.

**Possible Outcomes:** Accepted/processing · Active/live · Rejected · Partially accepted · Missing information · Validation failure · Pending marketplace review · Account/category permission issue.

**Rule:** Keep checking until a terminal state is reached or a human action is required.

STEP 11

### FIX ERRORS

**Goal:** Diagnose and resolve errors without making the seller repeat the process.

**For every error:** Capture error code/message; identify affected SKU/field; translate to plain language; determine if auto-fixable; apply deterministic fix; revalidate.

**Auto-Fixable Classes:** Wrong portal enum mapped from known canonical value; formatting issue; safely calculable derived field; incorrect parent/child mapping.

**Human-Required Classes:** Missing factual product info; conflicting seller data; brand authorization/approval; account issue; compliance evidence request.

STEP 12

### RESUBMIT

**Goal:** Send the corrected listing back to the marketplace.

**Actions:** Keep same seller SKU/identity; record correction made; increment submission attempt count; submit only after validation passes; preserve failed versions for audit.

STEP 13

### CONFIRM LIVE

**Goal:** Confirm the product is genuinely sellable/live.

**Minimum Confirmation:** Status = live/active; marketplace ID captured; seller SKU mapped; variant status captured; live URL captured where available; latest successful sync timestamp recorded.

**Output:** `LIVE` status.

STEP 14

### SHOW DASHBOARD STATUS

**Goal:** Give the seller a simple operational view.

**Show:** Overall status; per-marketplace status; current step; issue count; human actions required; last sync; marketplace listing ID/SKU; live URL; attempt history.

Core Dashboard Mandate

The dashboard should answer: _"What is live, what is not live, why, and what do I need to do?"_

27.  Capture error exactly as returned.

## 16\. Human-in-the-Loop Rules

The product should be autonomous by default, but not reckless. Human involvement is a controlled exception.

Ask the Seller When

Do NOT Ask When

A critical factual field is genuinely missing.

The answer already exists in the canonical record.

Two authoritative sources conflict.

The value can be deterministically normalized.

Marketplace requires seller-specific approval/evidence.

The agent can safely transform an existing value.

A compliance declaration cannot be verified.

The missing value is merely a formatting variation.

A category/brand permission decision is required.

The marketplace has a known mapping for the category.

## 21\. Example: One Apparel Product Through the System

Product Specification Case Study

**Product:** Women's relaxed-fit cotton T-shirt, Black, sizes S/M/L/XL, seller SKU `FSH-TEE-001`.

Stage

What Happens

**Intake**

Seller provides SKU, product images, product name, brand, fabric composition, colors, sizes, MRP, care instructions and size chart.

**Understand**

Agent identifies a women's T-shirt, black color, relaxed fit, cotton composition and four sizes.

**Classify**

Agent maps the product to the appropriate apparel/T-shirt category for each selected marketplace.

**Extract**

Agent normalizes 'Jet Black' to the marketplace's accepted black value where appropriate, while preserving the seller value.

**Canonical**

One product record contains identity, attributes, variants, media, compliance and content.

**Generate**

Agent creates title, bullets, description and relevant keywords using only verified facts.

**Validate**

Checks all marketplace-specific mandatory/conditional fields and variant/media rules.

**Human**

If a marketplace requires a missing fabric detail, the agent asks one targeted question.

**Submit**

Agent submits the marketplace-specific representation.

**Error**

Marketplace rejects one size because the size value is invalid. Agent maps the canonical size to the accepted marketplace value and revalidates.

**Resubmit**

Corrected listing is submitted.

**Live**

Marketplace confirms the listing active. Listing ID and URL are stored.

**Dashboard**

Product shows LIVE for that marketplace and separate statuses for any other marketplaces still processing.

## 24\. Handoff to Lead Engineer: What Must Be Clear Before Build

*   **Canonical product is the source of truth;** marketplace listings are derived representations.
*   **Marketplace schemas are versioned and can change.**
*   **Every field should have a source**, and critical facts should have confidence/evidence.
*   **Required fields are marketplace + category + context dependent.**
*   **Variant relationships are first-class product data**, not just a UI feature.
*   **Listing status is per marketplace** and per variant where necessary.
*   **Errors are first-class records** with classification, severity and resolution state.
*   **Human questions are first-class workflow tasks**, not generic support tickets.
*   **Every submission and correction should be auditable.**
*   **The workflow must be resumable.** If a seller answers one question, the agent continues from the blocked step rather than restarting the entire job.
*   **The agent must be idempotent at the business level:** repeated status checks or safe retries should not create duplicate product identities.
*   **Preserve separation:** The system should preserve marketplace-specific data without polluting the canonical product with marketplace-only fields.

## Day-45 Definition of Done

On Day 45, a real D2C brand user must be able to perform the complete journey end-to-end in production without any manual engineering intervention:

*   **Sign in & Tenant Isolation:** Sign in securely via JWT, select a brand, and maintain 100% tenant-scoped data isolation.
*   **Marketplace OAuth:** Connect an Amazon and/or Flipkart account via OAuth with credentials encrypted at rest.
*   **Product Import:** Import products via CSV (bulk) or manual entry with automated validation and image upload to GCS.
*   **AI Listing Generation:** Trigger AI generation for title, bullets, description, keywords, and attributes conditioned on the brand's voice guide via pgvector RAG.
*   **Deterministic & Vision Validation:** View deterministic rule failures and vision-based image compliance issues formatted as unified, structured errors.
*   **Bounded Self-Correction:** Watch the system automatically repair field-level errors (max 3 retries) and block gracefully when human intervention is needed.
*   **Maker-Checker Approval:** Review listings side-by-side per marketplace, edit fields, and approve or reject with audit trail (creator cannot approve own listing).
*   **Marketplace Publishing:** Publish approved listings via marketplace adapters with per-field success/failure reporting and live operational analytics.

## 10 Non-Negotiable Architectural Invariants

These 10 invariants are non-negotiable for the entire 45 days and beyond. Under deadline pressure, no engineer is permitted to cut corners on these rules:

Non-Negotiable Architecture Invariants

1.  **AI never publishes directly:** Only adapters publish, and strictly after human approval.
2.  **Rules Engine is deterministic code:** It is never an LLM call; rules are deterministic code and the final arbiter.
3.  **Human approval is mandatory in MVP:** There is zero unvetted auto-publishing in Phase 1.
4.  **Marketplace logic stays inside adapters:** The canonical listing model never contains marketplace-specific schema structures.
5.  **Mandatory tenant isolation on every query:** `tenant_id` scoping is enforced at the repository base class, with zero exceptions.
6.  **Marketplace credentials never enter LLM prompts:** Tokens are encrypted at rest with Cloud KMS and kept strictly isolated from AI contexts.
7.  **Observable AgentRuns:** Every generation call persists an `AgentRun` record logging model, token usage, cost, duration, and status.
8.  **Unified ErrorReport shape:** Rules engine, vision model, and marketplace API failures all return the exact same structured error contract.
9.  **Bounded retries (max 3):** Agent correction loops are capped at 3 attempts; no infinite loops ever exist.
10.  **Idempotent mutations & partial retries:** Partial marketplace failures retry only the specific failed field, never the entire listing.

## Core Operational Loop

This is the core operational loop repeated to the team at every standup:

Core Execution Rhythm

**AI proposes** → **Deterministic rules validate** → **Humans approve** → **Adapters execute** → **Performance feeds back**

## Kickoff Constraints & Solo Phase

During the first 10 days, you build solo. You do not build broad; you build a **razor-thin vertical slice** that validates the architecture: one category, one marketplace's rules, and one end-to-end AI call. Days 11–14 have a 4-day slack buffer designed to absorb any solo slippage before full-throttle scaling.

## Solo Sprint Reality Check (Days 1–10)

Ten days is tight for Days 1–10 because it compresses roughly two weeks of 5-person work into one person. Two strict principles make it survivable:

1.  **Ruthless Scope Discipline:** In the solo phase you build the _thinnest possible vertical slice_ that proves the architecture. One category, one marketplace's rules, a handful of rule checks, and one real LLM call. Breadth is added only once the team arrives.
2.  **Never Cut Invariants:** Never skip tenant isolation or schema correctness to hit Day 10 exactly. Retrofitting tenant scoping or migrating schema under live traffic is 10x more expensive than spending an extra half-day getting it right initially.

## Core Runtime Flow & Batch Behavior

End-to-End Runtime Pipeline

`Request → Context Assembly (Brand RAG + Rules) → Parallel Agents (Content, Keyword, Attribute, Image) → Canonical JSON → Schema Validation → Deterministic Rules + Vision Checks → Structured ErrorReport → Field Correction (≤3) → Quality Score → Human Approval → Marketplace Adapter → Per-Field Publish Result.`

**Batch Import Resilience:** When a user uploads a CSV with 500 rows, each row is parsed individually and fans out into bounded-concurrency async jobs in Redis+ARQ. A malformed row or single-item rule violation never fails the batch. The batch completes with a per-row summary report.

## PostgreSQL 16 Schema (Full DDL)

This is the consolidated database schema. Every multi-tenant table carries `tenant_id` or `brand_id` (foreign key to `tenants.id`):

database\_schema\_v1.sql

```sql
-- 1. Tenants / Brands
CREATE TABLE tenants (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name TEXT NOT NULL,
  tone TEXT,
  guidelines JSONB,
  glossary JSONB,
  created_at TIMESTAMPTZ DEFAULT now()
);

-- 2. Users / RBAC Roles
CREATE TABLE users (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID REFERENCES tenants(id) NOT NULL,
  email TEXT NOT NULL,
  hashed_password TEXT,
  role TEXT NOT NULL CHECK (role IN ('owner','operator','reviewer','admin')),
  created_at TIMESTAMPTZ DEFAULT now(),
  UNIQUE (tenant_id, email)
);

-- 3. Brand Chunks (pgvector RAG Store)
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE brand_chunks (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  brand_id UUID REFERENCES tenants(id) NOT NULL,
  type TEXT NOT NULL,              -- tone_rule | glossary | compliance | example
  text TEXT NOT NULL,
  embedding vector(1536),
  updated_at TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX brand_chunks_embedding_idx ON brand_chunks
  USING hnsw (embedding vector_cosine_ops);

-- 4. Products (Canonical Input)
CREATE TABLE products (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  brand_id UUID REFERENCES tenants(id) NOT NULL,
  sku TEXT NOT NULL,
  title TEXT NOT NULL,
  images JSONB,
  attributes JSONB,
  status TEXT DEFAULT 'draft',
  created_at TIMESTAMPTZ DEFAULT now(),
  updated_at TIMESTAMPTZ DEFAULT now(),
  UNIQUE (brand_id, sku)
);

-- 5. Marketplace Accounts (Encrypted Credentials)
CREATE TABLE marketplace_accounts (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  brand_id UUID REFERENCES tenants(id) NOT NULL,
  marketplace TEXT NOT NULL,        -- amazon | flipkart
  token_enc BYTEA NOT NULL,         -- KMS-wrapped AES-256 ciphertext
  status TEXT DEFAULT 'active',
  created_at TIMESTAMPTZ DEFAULT now()
);

-- 6. Listings (Marketplace Entity)
CREATE TABLE listings (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  product_id UUID REFERENCES products(id) NOT NULL,
  marketplace TEXT NOT NULL,
  status TEXT NOT NULL,             -- created|generating|validated|needs_review|approved|publishing|published|blocked|failed
  external_id TEXT,
  created_at TIMESTAMPTZ DEFAULT now()
);

-- 7. Listing Versions (Maker-Checker Integrity)
CREATE TABLE listing_versions (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  listing_id UUID REFERENCES listings(id) NOT NULL,
  version INT NOT NULL,
  content_json JSONB NOT NULL,
  image_reports_json JSONB,
  generated_by_user_id UUID REFERENCES users(id),
  approved_by_user_id UUID REFERENCES users(id),
  created_at TIMESTAMPTZ DEFAULT now(),
  -- Architectural Invariant: Creator cannot approve own listing
  CHECK (approved_by_user_id IS NULL OR approved_by_user_id <> generated_by_user_id)
);

-- 8. Deterministic Rules
CREATE TABLE rules (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  marketplace TEXT NOT NULL,
  category TEXT,
```

## Listing Lifecycle State Machine

Every listing moves through a strictly bounded state machine with bounded self-correction retries (max 3):

**Architecture Diagram: Listing Lifecycle State Machine**

```mermaid
stateDiagram-v2
    [*] --> QUEUED
    QUEUED --> LOADING_CONTEXT
    LOADING_CONTEXT --> GENERATING
    GENERATING --> SCHEMA_VALIDATING
    SCHEMA_VALIDATING --> RULE_VALIDATING
    RULE_VALIDATING --> VISION_VALIDATING
    VISION_VALIDATING --> CORRECTING : validation failed
    CORRECTING --> SCHEMA_VALIDATING : retry attempt (max 3)
    CORRECTING --> BLOCKED : 3 attempts exhausted
    VISION_VALIDATING --> QUALITY_CHECK : all checks passed
    QUALITY_CHECK --> NEEDS_APPROVAL
    NEEDS_APPROVAL --> APPROVED : human approved
    NEEDS_APPROVAL --> CORRECTING : rejected with feedback
    APPROVED --> PUBLISHING
    PUBLISHING --> PUBLISHED : adapter success
    PUBLISHING --> FAILED : unrecoverable adapter error
    BLOCKED --> [*]
    FAILED --> [*]
    PUBLISHED --> [*]
```

## LangGraph Execution Graph

The LangGraph graph executes in-process on the background worker:

load\_context (Fetch product + marketplace rules + tenant profile)

↓

retrieve\_brand\_voice (pgvector top-k=8 cosine search over brand\_chunks)

↓

parallel\_agents \[Content, Keyword, Attribute, Image Analyzers\]

↓

merge\_outputs (Assemble Canonical Listing JSON)

↓

validate\_schema (Pydantic structural check)

↓

validate\_rules (Deterministic Rules Engine check)

↓

validate\_vision (Vision model image compliance check)

↓

classify\_errors & correct\_fields (Bounded self-correction <= 3 retries)

↓

quality\_score (Compute confidence score)

↓

human\_approval\_interrupt (Pause for human review & maker-checker)

↓

publish (Adapter executes marketplace mutation)

Publish Authority Invariant

The LangGraph graph never possesses publish authority. Even if an AI agent prompts to publish, the FastAPI publishing router validates human approval server-side before invoking the adapter.

## Deterministic Rules Engine

The Rules Engine is plain, unit-testable Python code — **never an LLM call**. It enforces marketplace rules deterministically:

*   **Length Boundaries:** Enforce strict character caps (e.g. Amazon title ≤ 200 chars; Flipkart title ≤ 150 chars).
*   **Banned Term Filtering:** Reject claims like "best seller", "free shipping", "guaranteed cure", or competitor trademarks.
*   **Required Category Attributes:** Ensure mandatory fields (size, color, material, care instructions) are present.

## Model Routing & Cost Observability Policy

To avoid silent LLM bill creep, model invocation follows a strict economic policy:

*   **Cheapest Default Route:** Route text and vision generation to the most cost-effective model meeting the quality bar.
*   **Escalation on Repeated Failure:** If structured JSON output validation fails twice on a run, escalate only that run to a stronger reasoning model tier.
*   **Dedicated Embedding Model:** Embeddings always use a lightweight text-embedding model; never use the generation model for embeddings.
*   **Mandatory Telemetry:** Every single call logs `model_used`, `tokens_in`, `tokens_out`, and `cost` into `agent_runs`.

## Prompt Injection Defense Boundary

Product-supplied text (titles, descriptions, manufacturer notes from CSV uploads) is ALWAYS treated as untrusted data, never as system instructions. Brand guidelines and marketplace rules are injected via dedicated system message structures, establishing an unbreachable prompt-injection boundary.

## MarketplaceAdapter Pattern (Python ABC)

Every marketplace interaction implements a strict abstract base class. All methods return per-field status, never a bare boolean:

marketplace\_adapter.py

```python
from abc import ABC, abstractmethod
from datetime import date
from pydantic import BaseModel
from typing import Dict, Any, List

class FieldResult(BaseModel):
    field: str
    status: str  # 'success' | 'failed'
    message: str | None = None

class ListingResult(BaseModel):
    marketplace: str
    overall_status: str  # 'published' | 'partial' | 'failed'
    external_id: str | None = None
    field_results: List[FieldResult]
    raw_error: Dict[str, Any] | None = None

class MarketplaceAdapter(ABC):
    @abstractmethod
    async def get_listing(self, sku: str) -> ListingResult: ...

    @abstractmethod
    async def create_listing(self, listing: Any) -> ListingResult: ...

    @abstractmethod
    async def update_listing(self, listing: Any) -> ListingResult: ...

    @abstractmethod
    async def publish_listing(self, listing: Any) -> ListingResult: ...

    @abstractmethod
    async def get_performance(self, listing_id: str, from_date: date, to_date: date) -> Any: ...
```

## Mandatory TenantScopedRepository Pattern

To prevent cross-tenant data leaks, all database operations inherit from a base repository that enforces `tenant_id` scoping automatically:

tenant\_repository.py

```python
class TenantScopedRepository:
    def __init__(self, db_session, tenant_id: UUID):
        self.db = db_session
        self.tenant_id = tenant_id

    def filter_tenant(self, query, model):
        """Enforce tenant isolation on every single query."""
        return query.filter(model.tenant_id == self.tenant_id)

    async def get_by_id(self, model, entity_id: UUID):
        stmt = select(model).where(
            model.id == entity_id,
            model.tenant_id == self.tenant_id
        )
        return (await self.db.execute(stmt)).scalar_one_or_none()
```

## Maker-Checker Integrity

Maker-Checker Rule

The user who generates or edits a listing CANNOT approve that listing. This is enforced at the database level via a `CHECK (approved_by_user_id IS NULL OR approved_by_user_id <> generated_by_user_id)` constraint, and confirmed in the API router before any publish operation is permitted.

## Async Queue & Job Lifecycle (Redis + ARQ)

All long-running tasks (CSV imports, LLM generation, vision analysis, marketplace publishing) run asynchronously:

API receives POST request → validates payload

↓

Enqueue task in Redis with unique job\_id and idempotency key

↓

Return 202 Accepted with job status URL immediately

↓

ARQ Worker executes job with exponential backoff on failure

↓

Status transitions: QUEUED → RUNNING → SUCCEEDED / FAILED / PARTIAL

↓

Frontend polls status or receives completion notification

## Distributed Correlation & Cost Telemetry

*   **Request ID Propagation:** Every request generates a UUID `request_id` propagated through contextvars, HTTP headers, worker jobs, and Cloud Trace spans.
*   **AgentRun Cost Telemetry:** Every AI call records `tokens_in`, `tokens_out`, model identifier, and computed USD cost.

## Why This Architecture

### Why Separate Intelligence, Control, and Execution?

**Intelligence** (AI agents) is probabilistic — it generates high-quality content but can hallucinate, violate marketplace rules, or drift from brand voice. **Control** (Rules Engine) is deterministic — it catches violations with certainty. **Execution** (Adapters) is marketplace-specific — it handles the complexity of each platform's API, auth, and rate limits.

Separating these concerns means:

*   You can change AI models without touching marketplace logic
*   You can add a new marketplace without modifying AI agents
*   You can update rules without redeploying agents
*   Each layer can be tested, monitored, and scaled independently

### Why AI Must Not Directly Publish

LLMs are powerful but non-deterministic. A language model might generate a title that violates Amazon's 200-character limit, include a medical claim that regulatory compliance forbids, or use a competitor's trademarked term. Deterministic validation between AI and execution ensures that:

*   Every character count is checked programmatically, not probabilistically
*   Banned terms are caught before they reach the marketplace
*   Category-specific attribute schemas are validated against known templates
*   Image compliance is verified through both pixel analysis and vision models

Architectural Invariant

AI never directly publishes data to any marketplace. The Rules Engine is deterministic. Human approval is required in MVP. These constraints are non-negotiable.

## Non-Technical Explanation

Non-Technical Explanation

Think of the system as having an AI writing assistant, a strict quality checker, a human reviewer, and a publishing service — working in sequence. The AI writes the listing content using the brand's voice and marketplace rules. The quality checker catches any violations or errors using strict, programmable rules (not AI). A human then reviews and approves. Only after approval does the system push the listing to Amazon or Flipkart. If the listing performs well, the system learns from that success for future listings.

## AI Implementation Context

AI Implementation Context

**What an AI coding agent must know before modifying this module:**

*   The four-layer separation is an architectural invariant — do not merge layers
*   All AI output must pass through the Rules Engine before human approval
*   The canonical listing model is marketplace-independent
*   Marketplace-specific logic lives exclusively in adapters
*   Performance data flows back to the Intelligence layer, not directly to Execution

**What this module must never do:**

*   Allow AI agents to bypass the Control layer
*   Put marketplace-specific fields in the canonical model
*   Allow the Experience layer to call marketplace APIs directly
*   Remove human approval in MVP

# [2] Architecture Principles

- **Section**: Overview
- **Scope**: MVP
- **URL**: https://ashishvats16.github.io/system-arch/page/architecture-principles
- **Description**: The foundational principles that guide every architectural decision in the platform. These principles are invariants — they should never be violated.
- **Keywords**: principles, invariants, rules, AI proposes, deterministic, human approval, adapter pattern

## Core Principles

Primary Principle

AI proposes → Deterministic rules validate → Humans approve → Adapters execute → Performance feeds back into optimization

Every system design decision must align with these principles:

### 1\. AI Is Advisory, Not Authoritative

AI agents generate content suggestions. They never have direct publish authority. All AI output is treated as a proposal that must pass through deterministic validation and human approval before reaching any marketplace.

### 2\. Deterministic Rules Are the Final Arbiter

The Rules Engine enforces marketplace constraints with certainty. No LLM output ships without passing it. Rules are programmable, versioned, and marketplace-specific. They catch what AI misses — character limits, banned terms, missing attributes, image specifications.

### 3\. Marketplace Independence via Canonical Model

The core listing representation is marketplace-agnostic. Amazon-specific fields, Flipkart-specific formats, and future marketplace requirements live inside their respective adapters. The canonical model never contains raw marketplace API structures.

### 4\. Adapter Pattern for Marketplace Operations

Every marketplace interaction happens through a well-defined adapter interface. Adding Myntra or Ajio later requires building a new adapter — not rewriting the core platform. Adapters own: auth refresh, rate limiting, idempotency, and error mapping.

### 5\. Tenant Isolation Is Mandatory

Every database query, every API call, every agent run is scoped to a tenant. Cross-tenant data leakage is a critical security violation. Tenant filtering is enforced at the repository layer, not at the application layer.

### 6\. Structured Errors Everywhere

Every failure — rules engine, vision model, marketplace API — returns the same structured ErrorReport envelope. This enables AI correction agents, UI display, logging, retry logic, and debugging from a single contract.

### 7\. Bounded Retries

All retry loops are bounded (max 3 for agent corrections). The system never enters infinite retry loops. Failed jobs surface exact reasons for human intervention.

### 8\. Observability by Default

Every AgentRun records: model\_used, tokens\_in, tokens\_out, cost, duration, status. Every marketplace call is logged. Every validation run is persisted. This creates a complete audit trail and cost observability.

## Architectural Invariants

Never Violate These Rules

1.  AI never directly publishes to marketplaces
2.  Rules Engine is deterministic — never an LLM
3.  Human approval is required in MVP
4.  Marketplace-specific logic belongs inside adapters only
5.  Canonical listing model is marketplace-independent
6.  Tenant isolation is mandatory on every query
7.  Marketplace credentials are encrypted at rest (AES-256)
8.  All AgentRuns are observable and persisted
9.  All failures use structured ErrorReport contracts
10.  Retries are bounded (max 3 for agent corrections)
11.  Marketplace mutations are idempotent
12.  Failed fields are retried individually, not the entire listing
13.  Optimization Agent runs on schedule, not continuously
14.  Future marketplaces don't require rewriting the core system

## Why These Principles Matter

*   **Reliability** — LLM can never bypass the Rules Engine; structured errors make every failure actionable
*   **Defensibility** — Brand-voice vectors + version history + performance feedback loop compound over time
*   **Marketplace independence** — Canonical model + adapters; adding Myntra/Ajio later is an adapter, not a rewrite
*   **Cost efficiency** — Event-driven generation (only when needed), model routing, and the optimization agent only fires on schedule, not continuously

## Maker-Checker Principle

Maker-Checker Rule

## Step-by-Step Walkthrough

### 1\. Connect

OAuth to Amazon SP-API and Flipkart Seller API. Tokens are encrypted at rest with AES-256 and stored in the `MarketplaceAccount` table. Token refresh is handled automatically by the adapters.

### 2\. Import

Three import modes: CSV bulk upload, manual entry, or brand catalog sync. CSV upload enters the async queue — each row is validated, then fanned out into parallel Agent Runs (bounded concurrency per marketplace to respect rate limits).

### 3\. Generate

AI generates text (title, bullets, description, keywords, attributes) and checks images. Brand voice is retrieved from pgvector embeddings. Agents run in parallel where no dependencies exist (Content, Keyword, Attribute, Image can execute concurrently).

### 4\. Validate

Deterministic rules engine + vision model return structured pass/fail via the unified ErrorReport. Rules check: character limits, banned terms, missing attributes, category compliance. Vision checks: background color, resolution, text overlays, watermarks.

### 5\. Approve

Human reviews the generated output alongside validation results, warnings, errors, confidence score, and marketplace differences. Options: Approve, Reject (with feedback), Edit, Regenerate. Rejection feedback is stored and can be used as future context.

### 6\. Publish

Adapters push to each marketplace with per-field result reporting. On partial success, only failed fields are retried — never the whole listing (idempotency keys on the marketplace side).

### 7\. Learn

Performance metrics (conversion, CTR, returns, ranking) feed the optimization loop. The Optimization Agent (Phase 3) proposes changes to existing listings based on performance data.

Before any agent runs, the system assembles a rich context object containing: product data, brand voice chunks (retrieved via pgvector cosine similarity), marketplace-specific rules, category template with required/optional attributes, previous listing versions (if any), and user instructions.

## Parallel Execution

Content Agent, Keyword Agent, Attribute Agent, and Image Agent can execute in **parallel** because they have no inter-dependencies — each reads from the shared context but produces independent outputs. The Agent Orchestrator (LangGraph) manages this parallelism and merges outputs into the canonical listing JSON.

Engineering Note

LangGraph supports parallel node execution via branching edges. Each agent node reads from the shared AgentState but writes to its own output field. The merge node combines all outputs into the final canonical listing.

## Engineering Implementation

Conceptual Agent Architecture

```python
class ListingAgent:
    """Orchestrates the complete listing generation pipeline."""
    
    def __init__(self, context_builder, retriever, prompt_builder, orchestrator):
        self.context_builder = context_builder
        self.retriever = retriever
        self.prompt_builder = prompt_builder
        self.orchestrator = orchestrator  # LangGraph instance
    
    async def generate(self, product_id: str, marketplace: str) -> ListingResult:
        # 1. Build context
        context = await self.context_builder.build(product_id, marketplace)
        
        # 2. Retrieve brand voice chunks
        brand_chunks = await self.retriever.retrieve(
            brand_id=context.brand_id,
            query=context.retrieval_query,
            top_k=8
        )
        context.brand_chunks = brand_chunks
        
        # 3. Build prompts for each sub-agent
        prompts = self.prompt_builder.build(context)
        
        # 4. Execute agent graph (parallel agents + validation + correction)
        result = await self.orchestrator.execute(context, prompts)
        
        return result
```

## AI Implementation Context

AI Implementation Context

**Inputs:** Product, Brand, Marketplace, Category, Rules, Previous versions, User instructions

**Outputs:** Canonical Listing JSON with metadata

**Dependencies:** pgvector (brand retrieval), LangGraph (orchestration), ModelRouter (model selection)

**Invariants:** All output passes through Rules Engine. Max 3 correction retries. Brand voice retrieval uses cosine similarity top-k=8.

**What this module must never do:** Bypass validation, publish directly, use hardcoded model names, ignore brand context, generate without marketplace rules loaded.

## LangGraph Architecture

LangGraph provides the orchestration framework for the AI Listing Agent. It models the generation pipeline as a directed graph with typed state, conditional edges, and built-in support for retries, human-in-the-loop interrupts, and state persistence.

### Why LangGraph

*   **Graph-based orchestration** — Models complex agent workflows as nodes and edges
*   **Typed state** — AgentState is a structured object that flows through the graph
*   **Conditional routing** — Branch based on validation results, retry counts, error types
*   **Human-in-the-loop** — Interrupt the graph at the approval node, resume after human decision
*   **Persistence** — State can be checkpointed and resumed after interrupts or failures
*   **Parallel execution** — Multiple nodes can execute concurrently via branching edges

Sequential vs Parallel

*   **Sequential (requires all):** Merge → Validate → Quality Check → Approval

## Engineering Implementation

Content Agent Pseudocode

```python
class ContentAgent:
    def __init__(self, model_router, prompt_builder):
        self.model_router = model_router
        self.prompt_builder = prompt_builder
    
    async def generate(self, context: AgentContext) -> ContentOutput:
        # 1. Build prompt with brand voice + rules
        prompt = self.prompt_builder.build_content_prompt(context)
        
        # 2. Select model via router
        model = self.model_router.select(
            task="content_generation",
            marketplace=context.marketplace,
            complexity=context.complexity_score
        )
        
        # 3. Call model with JSON mode
        response = await model.generate(
            messages=prompt.messages,
            response_format=ContentOutputSchema,
            temperature=0.7
        )
        
        # 4. Validate structured output
        output = ContentOutputSchema.model_validate_json(response)
        
        return output
```

Non-Technical Explanation

The Content Agent is like a skilled copywriter who knows your brand's voice, understands each marketplace's requirements, and never makes up product facts. It reads your product data, studies your brand's writing style, checks the marketplace's rules, and writes optimized titles, bullet points, and descriptions — all while staying factually accurate.

- **Section**: AI Agents

- **Description**: How new agents can be registered and integrated into the platform without rewriting core infrastructure.
- **Keywords**: agent registry, future agents, extensibility, plugin, registration

## Registry Design

The agent registry pattern allows new agents to be added without modifying the core orchestration layer. Each agent implements a standard interface:

```python
class AgentInterface(ABC):
    """Standard interface for all agents."""
    name: str
    version: str
    scope: str  # "mvp" | "phase2" | "phase3" | "future"
    
    @abstractmethod
    async def execute(self, context: AgentContext) -> AgentOutput: ...
    
    @abstractmethod
    def get_input_schema(self) -> dict: ...
    
    @abstractmethod
    def get_output_schema(self) -> dict: ...
```

New agents register with the orchestrator and plug into the existing data layer, validation pipeline, and observability infrastructure. This is how the Listing Agent can expand into the full Marketplace OS without platform rewrites.

## Why a Dedicated Pipeline

Amazon and Flipkart reject listings silently or visibly for image violations — white-background rules, resolution, text overlays, watermarks. This pipeline runs **before human approval, in parallel with text generation**. Catching image issues early prevents wasted publishing attempts.

## Pipeline Flow

**Architecture Diagram: Image Compliance Pipeline**

```mermaid
graph TD
  UP["Image Upload"] --> S3["Store in S3"]
  S3 --> DET["Deterministic Checks"]
  DET -->|"resolution, format, aspect ratio, EXIF"| VIS["Vision Model Review"]
  VIS -->|"background, fill, text, watermark"| RPT["Structured ImageReport"]
  RPT --> CHECK{"Pass/Warn/Fail?"}
  CHECK -->|"Pass"| ATTACH["Attach to listing"]
  CHECK -->|"Fail/Warn"| FEEDBACK["Surface issue + suggested fix"]
  FEEDBACK --> USER["User reviews"]
  USER -->|"Fix & re-upload"| UP
  USER -->|"Accept warning"| ATTACH
```

## Architecture

Marketplace-specific rules are stored as policy configurations — NOT hardcoded into the vision agent. Amazon and Flipkart image rules are separate policy documents that the pipeline evaluates against. This means adding a new marketplace's image rules requires only a new policy configuration, not code changes.

Invariant

Marketplace image rules are policy configurations, not hardcoded logic. The vision agent evaluates images against loaded policies.

## Adapter Interface

MarketplaceAdapter ABC

```python
class MarketplaceAdapter(ABC):
    async def get_listing(self, sku) -> ListingResult
    async def create_listing(self, listing) -> ListingResult
    async def update_listing(self, listing) -> ListingResult
    async def publish_listing(self, listing) -> ListingResult
```

## Adapter Responsibilities

*   Every method returns `ListingResult` with per-field success/failure, not a boolean
*   On partial success, return exactly which fields failed + marketplace's raw error string
*   Adapters own: auth refresh, rate limiting, idempotency, error mapping to unified ErrorReport
*   Canonical model → marketplace-specific mapping happens inside the adapter
*   The rest of the system never touches raw marketplace APIs

```mermaid
graph LR
```

## Why Async

Marketplace API calls are slow (seconds to minutes). AI generation takes 5-30 seconds. Bulk imports process hundreds of products. None of these should block the HTTP request cycle. The async architecture uses Redis as a message broker with ARQ as the task queue framework.

```mermaid
  DB --> UI["UI Status Update"]
```

The API returns immediately with a job ID (HTTP 202). The client polls for status or receives webhook notifications.

## pgvector

# [221] Architectural Invariants

- **Section**: Engineering
- **Scope**: MVP
- **URL**: https://ashishvats16.github.io/system-arch/page/architectural-invariants
- **Description**: The non-negotiable architectural rules that must never be violated.
- **Keywords**: architectural invariants, rules, non-negotiable, constraints

## Architectural Invariants

Never Violate These Rules

1.  AI never directly publishes to marketplaces
2.  Rules Engine is deterministic — never an LLM
3.  Human approval is required in MVP
4.  Marketplace-specific logic belongs inside adapters only
5.  Canonical listing model is marketplace-independent
6.  Tenant isolation is mandatory on every query
7.  Marketplace credentials are encrypted at rest (AES-256)
8.  All AgentRuns are observable and persisted
9.  All failures use structured ErrorReport contracts
10.  Retries are bounded (max 3 for agent corrections)
11.  Marketplace mutations are idempotent
12.  Failed fields are retried individually, not the entire listing
13.  Optimization Agent runs on schedule, not continuously
14.  Future marketplaces don't require rewriting the core system

These invariants are the foundation of the system's reliability, security, and extensibility. Any modification to the codebase — by a human or an AI coding agent — must preserve these invariants.

AI Implementation Context

If you are an AI coding agent reading this: these invariants are non-negotiable. Do not bypass the Rules Engine, do not allow direct publishing, do not mix marketplace logic into the canonical model, and do not remove tenant isolation. If you need to change something that appears to conflict with an invariant, escalate to a human architect.
