# mkos-schemas changelog

The Python package `mkos-schemas` and the npm package `@maniacultasset/schemas` (installed by the FE
as `"@mkos/schemas": "npm:@maniacultasset/schemas@<version>"`) share one version, released by one
`schemas-v<version>` tag.

**Version rule after a tag.** Any PR that changes the contract (`jsonschema/**`, `ts/src/**`, the
`mkos_schemas` models, or `openapi.json` through the API registry) once `schemas-v<current>` exists:

- If this file has an open `## 1.N.0 (unreleased)` heading, add the entry under it.
- Otherwise bump to the next MINOR in one commit: `packages/schemas/pyproject.toml`,
  `packages/schemas/ts/package.json`, `SCHEMA_VERSION` in `src/mkos_schemas/base.py`, every fixture's
  `schema_version`, and the regenerated outputs; then open `## 1.N.0 (unreleased)`.
- A description-only change may take a PATCH instead, unless a MINOR heading is already open.
- Classify each change first (docs/RULES.md §11): adding a member to a closed vocabulary (an error
  code to a declared set included) is MAJOR and waits for its window.
- The tagging PR closes the heading (`## 1.N.0 (YYYY-MM-DD)`). The publish workflow refuses a tag
  whose heading is still `(unreleased)`, and `make contracts` refuses contract changes at an
  already tagged version (`scripts/ci/schemas_version_check.sh`).

## 1.1.0 (unreleased)

- Marketplace preview (S20, additive MINOR after `schemas-v1.0.0`): `GET /api/v1/listings/{listing_id}/preview` answers `MarketplacePreview {schema_version, listing_id, version, marketplace, product_type, items, report}`, so 44 operations (43 on main after S16, plus this one). Each `PreviewItem {product_id, seller_sku, item_role, payload}` is what the marketplace adapter would send for one SKU (`item_role` is `standalone`, `parent` or `child`; a family lists the parent first, then the children by SKU); images appear as `image:<id>` references, never URLs. `product_type` is null when the listing's pinned template is not mapped for the marketplace, and `report` (an `ErrorReport`) lists the adapter's mapping errors (CATEGORY_NOT_MAPPED, REQUIRED_FIELD_MISSING, VALUE_NOT_ALLOWED, VARIATION_INVALID). The preview carries no verdict and sends nothing; it needs no marketplace account. Errors: 404 `NOT_FOUND` (unknown or another tenant's listing), 409 `LISTING_BUSY` (no version yet, or generating), 501 `NOT_IMPLEMENTED` (a marketplace with no adapter yet: Flipkart until S22). **FE:** show it as the "what will be sent" panel before approval; read errors from `report.errors`.
- Review and approval (S19, additive MINOR under the open 1.1.0): four operations, so 48. `GET /api/v1/listings/{listing_id}/history` answers `ListingHistoryPage` of `AuditEventOut {id, action, actor_type, actor_user_id, entity_type, entity_id, before, after, reason, request_id, job_id, occurred_at}` (newest first; no actor email or IP). `GET /api/v1/issues` answers `IssuePage` of `IssueOut` (the issue row without its internal keys; filters `status` (default `open`), `listing_id`, `source`, `error_code`, `marketplace`). `POST /api/v1/issues/{issue_id}/dismiss` (Idempotency-Key; reviewer or owner) answers `IssueOut` and refuses an error or a closed issue with 409 `INVALID_STATUS_TRANSITION`: only warnings can be accepted. `GET /api/v1/tasks` answers `TaskPage` of `TaskOut` (no `evidence`, no `answer`; filter `status`, default `open`). `GET /api/v1/listings/{listing_id}` and `PATCH /api/v1/listings/{listing_id}/content` now declare an `ETag` response header: the current version id, quoted, to send back as `If-Match`. `POST /api/v1/listings/approve` is live: the approver is the token's user, and whoever generated or edited the version (back to the last full generation) gets an item 403 `MAKER_CHECKER_VIOLATION`; `feedback` refuses control characters other than newline and tab (422). **FE:** use `GET /listings?status=validated` (or `needs_review`) as the review queue, oldest first; the request answers 200 and each item carries its own `http_status` and `error` in `BatchResult.items`.
- Publish, per-field retry and status sync (S21, additive MINOR under the open 1.1.0): two operations, so 50. `GET /api/v1/listings/{listing_id}/submissions` (every role; keyset `limit`/`cursor`, newest first) answers `SubmissionPage` of `SubmissionOut {id, listing_version_id, attempt (1-3), operation (create|update|patch), field_paths, outcome (pending|accepted|partially_accepted|rejected|error|live|superseded), error_code, retry_justification, requested_by_user_id, items, error, sent_at, responded_at, resolved_at, created_at}`; each `SubmissionItemOut {listing_item_id, seller_sku, marketplace_state, fields}` carries the attempt's per-field `FieldResult`s. No storage key, digest or raw marketplace body is ever returned. `POST /api/v1/listings/{listing_id}/refresh-status` (owner or operator; Idempotency-Key) answers 202 `JobAccepted` and checks the marketplace now: 409 `INVALID_STATUS_TRANSITION` unless the listing is `published` (or `failed/publish_partial` after a partial accept), 409 `LISTING_BUSY` while publishing, 429 `RATE_LIMITED` for a second refresh of one listing within 5 minutes. `PublishItem` gains an optional `listing_version_id`: when given and not the current version the item is 409 `STALE_VERSION`. `POST /api/v1/listings/publish` and `POST /api/v1/listings/{listing_id}/publish/retry-fields` are live; retry-fields resends only the fields whose latest result failed and declares 409 `DUPLICATE_SUBMISSION_BLOCKED`, `INVALID_STATUS_TRANSITION`, `LISTING_BUSY`, `SUBMISSION_ATTEMPTS_EXHAUSTED` and `AUTH_EXPIRED` (no connected account). A publish job's `JobEnvelope.result_url` is the listing's submissions path. **FE:** show `published` with `marketplace_state = processing` as "Submitted" (not live) until a status sync confirms it; offer retry-fields on `failed/publish_partial` and read the per-field verdicts from the submissions page.
- Analytics (S23, additive MINOR under the open 1.1.0; no new operation, still 50): `GET /api/v1/analytics` and `GET /api/v1/analytics/summary` are live. `from` and `to` are now optional (both absent: the last 30 UTC days ending today; only `to`: the 30 days ending `to`; only `from`: `from` to today); the range is inclusive UTC days, at most 366 days, `from` after `to` is 422 `VALIDATION_FAILED`. `AnalyticsSummary` gains optional `counts` (`AnalyticsCounts {listings_generated, approvals, rejections, validation_first_pass_passed, validation_first_pass_total, publish_succeeded, publish_failed}`, the counts behind each rate) and `by_marketplace` (at most 2 `MarketplaceBreakdown {marketplace, listings_generated, approval_rate, validation_pass_rate, publish_success_rate, counts}`, only marketplaces with any activity, in enum order). Rates are shares in [0, 1] rounded half-even to 4 places, null when the denominator is 0. Formulas: volume = versions of origin `generation` or `regeneration` created in range; approval rate = approvals / (approvals + rejections) decided in range (`regenerate_requested` excluded); validation pass rate = first-attempt Rules Engine runs that passed / all first-attempt Rules Engine runs in range; publish success rate = submissions answered in range with outcome accepted, live or superseded / those plus partially_accepted, rejected and non-retryable error (pending and retryable error rows excluded). A tenant may hold at most 2 analytics requests in flight (a third is 429 `RATE_LIMITED`). **FE:** read the rates as nullable; show `counts` as the denominators.
- Flipkart behind a flag (S22, additive under the open 1.1.0): `POST /api/v1/marketplaces/connect`, `GET /api/v1/marketplaces/{marketplace}/callback` and `POST /api/v1/marketplaces/connect/confirm` now declare 501 `NOT_IMPLEMENTED`. They already answered it for a marketplace that is not configured; they now also answer it, with the message "Flipkart is not enabled", while the deployment keeps Flipkart switched off (`FLIPKART_ENABLED=false`, the launch default). No type, field or code changes. `GET /api/v1/listings/{listing_id}/preview` now previews Flipkart listings too (no 501 for Flipkart): a Flipkart family lists its children only (Flipkart has no parent row), each child carrying its `style_code` and colour group, and `product_type` is the Flipkart vertical. **FE:** show "Flipkart is not enabled" from the envelope's `message` on a 501 from these routes, and keep the Flipkart connect button visible but expect the 501 until launch.
- Flipkart publish behind the flag (S22b, additive under the open 1.1.0): `POST /api/v1/listings/{listing_id}/publish/retry-fields` now declares 501 `NOT_IMPLEMENTED`: a Flipkart listing while `FLIPKART_ENABLED=false` answers the whole-request envelope with the message "Flipkart is not enabled" (nothing is stored under the Idempotency-Key, so the same key works once the flag is on). `POST /api/v1/listings/publish` keeps its 202: a Flipkart item while the flag is off is an item `http_status` 501 with that message in its `error` (no job; Amazon items in the batch are accepted as usual), and another tenant's or an unknown id stays an item 404. With the flag on, Flipkart listings publish, retry only their failed fields and sync like Amazon ones. No type, field or code changes. **FE:** show the item's `error.errors[0].message` for an item 501, and expect it for Flipkart items until launch.

## 1.0.0

First contract release. It ships outside the 4 Oct window as a one-time exception: nothing is pinned to 0.0.0. Later breaking changes wait for 18 Oct or 1 Nov.

Adding a member to a closed vocabulary (an enum, a `Literal`, a `RuleDef` union, or a path) is a breaking change.

- Requires Python `==3.13.*` and `pydantic>=2.11,<3`.
- `ImportReport` uses `import_id`, not `batch_id`.
- `ErrorCode` has 76 members. The 11 API codes added for the `/api/v1` surface (S3): `UNAUTHENTICATED`, `PERMISSION_DENIED`, `NOT_FOUND`, `METHOD_NOT_ALLOWED`, `IDEMPOTENCY_KEY_REUSED`, `STALE_VERSION`, `PAYLOAD_TOO_LARGE`, `NOT_IMPLEMENTED`, `OAUTH_STATE_INVALID`, `LAST_OWNER_REQUIRED` and `MARKETPLACE_ACCOUNT_CONFLICT`. None has an `ErrorClass`; `NOT_IMPLEMENTED` is `system_failure`, the rest `user_action`.
- Frozen status vocabularies: `ListingStatus` (9), `ListingResult.status` (3), `MarketplaceState` (8), `JobState` (7).
- `ImageRef` refuses `packaging_label` on a publishable listing. `ImageReport` may still name that slot.
- `GenerationContext.product` stays a dict through v1; the `facts.py` retype moves to after v1.
- New generated outputs (S3): `jsonschema/openapi.json` (the frozen `/api/v1` surface: 35 operations at S3, one error envelope, keyset pages) and the TypeScript types `ts/src/{api.d.ts,contracts.d.ts,index.ts}`, published as `@maniacultasset/schemas` (FE alias `@mkos/schemas`).
- Products (S12; still 1.0.0 because `schemas-v1.0.0` is not tagged yet): `POST /api/v1/products`, `GET /api/v1/products` and `GET /api/v1/products/{product_id}` go live. `ProductCreate.category` and `ProductOut.category` are now **required** slugs (the user decided this on 2026-10-06, TEAM-QUESTIONS T115; `products.category` is NOT NULL). Before this, the types marked `category` optional while the API refused a create without it (422). **FE/AI:** always send `category`. The oasdiff check carries the approved change in `scripts/ci/oasdiff-err-ignore.txt`.
- Auth and members (S10, additive; still 1.0.0 because `schemas-v1.0.0` is not tagged yet): `POST /api/v1/auth/switch-tenant` (`SwitchTenantRequest {target_tenant_id}`, answers `TokenResponse`), `GET /api/v1/members` (`MemberPage` of `MemberOut`) and `PATCH /api/v1/members/{user_id}` (`MemberPatch {role?, is_active?}`, 409 `LAST_OWNER_REQUIRED`), so 38 operations. Every operation carries `x-mkos-action` (the action it requires, or `public`), and the 403 `PERMISSION_DENIED` responses follow the role x action matrix: `images/upload-url`, `images/upload`, `listings/validate`, `rules/dry-run`, `jobs/{job_id}/cancel` and `brand/documents` now declare it.
- Marketplace connect (S15, additive; still 1.0.0 because `schemas-v1.0.0` is not tagged yet): `POST /api/v1/marketplaces/connect/confirm` (`ConnectConfirmRequest {pending}`, the 43-character handle; answers `MarketplaceAccountOut`; 409 `MARKETPLACE_ACCOUNT_CONFLICT` when the seller account is already live, here under another seller or in another tenant, and 409 `OAUTH_STATE_INVALID` for an unknown, used, expired or foreign handle) and `POST /api/v1/marketplaces/accounts/{account_id}/revoke` (answers `MarketplaceAccountOut`; revoke deletes the stored tokens only, the brand removes the app in Seller Central or the Flipkart seller dashboard), so 40 operations. The callback also takes Amazon's `spapi_oauth_code` and `selling_partner_id` (`^[A-Za-z0-9]{1,64}$`); `code` becomes optional, and exactly one of `code` and `spapi_oauth_code` is required. **FE:** open `authorize_url` from `POST /marketplaces/connect`; on `/marketplaces/connected` read `pending`, POST it to `/marketplaces/connect/confirm` with the same user's token, and strip `pending` from the URL and history (`history.replaceState`).
- Rules (S14b, text only; still 1.0.0 because `schemas-v1.0.0` is not tagged yet): `GET /api/v1/rules` and `POST /api/v1/rules/dry-run` go live. The dry-run operation's `description` now states that it knows no product facts and no marketplace account (a rule conditioned on `product.*` or `account.*` never applies there), that an unknown marketplace and category pair is 422 `VALIDATION_FAILED` on `listing.category`, and that its body is capped at 256 KiB. No type changes. **FE:** read the dry-run as a rules preview only.
- The attribute dictionary (S13b, additive; still 1.0.0 because `schemas-v1.0.0` is not tagged yet): `mkos_schemas/data/attribute_dictionary.json` ships in the wheel. It lists every canonical fact key (82: identity, classification, commercial, compliance and dimension keys backed by typed columns, the brand-level `brand_profiles` keys, and the attribute and care keys, A.6 included) with its storage, owner levels, value type, input aliases (`material` → `fabric_type`), criticality and allowed sources; a `column` key names the typed columns it maps (`attribute_columns`). The migrator loads it with `python -m app.cli dictionary sync`. **FE/AI:** read key names and aliases from this file, never hard-code them.
- Imports (S13b): `POST /api/v1/products/bulk` declares 422 `IMPORT_FAILED` (a header or file problem: one `ErrorReport` at `file.header` or `file.row`, in the envelope's `error_report`), and `POST /api/v1/imports/{import_id}/rows/retry` declares 409 `INVALID_STATUS_TRANSITION` (a live job, or no failed rows).
- Brand onboarding (S16, additive; still 1.0.0 because `schemas-v1.0.0` is not tagged yet): `PATCH /api/v1/tenants/me` (`TenantPatch {name?, tone?, guidelines?, glossary?}`, at least one field; `tone: null` clears the tone; `If-Match` is required and 409 `STALE_VERSION` answers a stale one), `GET /api/v1/brand/documents` (`BrandDocumentPage` of `BrandDocumentOut {id, filename, status, chunk_count, error, created_at}`) and `DELETE /api/v1/brand/documents/{document_id}` (204), so 43 operations. `GET` and `PATCH /tenants/me` answer an `ETag` header. `POST /api/v1/brand/documents` takes an optional form field `type` (`tone_rule`, the default, `glossary` or `compliance`) and is owner/admin only. **FE:** send `If-Match` with the `ETag` from `GET /tenants/me`; uploads accept UTF-8 `.txt`/`.md` files up to 10 MiB (the request cap, so the file itself must be a little smaller); upload and delete are owner/admin only.
- Not in this release: `facts.py`, `batches.py` (the approve and publish batch shapes ship as API models in `openapi.json`), and `CanonicalListing.attribute_sources`.
